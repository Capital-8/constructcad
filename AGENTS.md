# AGENTS.md

Guidance for AI coding agents working in this repository.

## Commands

```sh
cargo run -p cc_app                                   # app (opens the home screen)
cargo run -p cc_app -- examples/casa_simples.ccad     # open a project
cargo run -p cc_app -- examples/casa_simples.ccad --view "Elevação: Sul" --lang en
cargo run -p cc_core --example casa_simples           # regenerate examples/casa_simples.ccad
cargo run -p cc_cli -- commands                       # the engine's command catalog (no GUI)
cargo run -p cc_cli -- -p examples/casa_simples.ccad run elements_list category=wall
cargo run -p cc_cli -- mcp                            # MCP server over stdio
cargo run -p cc_cli -- lua examples/small_house.lua width=10   # a Lua script
cargo run -p cc_cli -- --plugins examples/plugins commands     # the catalog with the example plugin's commands
cargo run -p cc_cli -- reference > docs/commands.md   # regenerate the command reference (a test checks it)

cargo nextest run --workspace                          # all tests (cargo-nextest)
cargo test --workspace --doc                          # doctests (nextest does not run them)
cargo nextest run -p cc_geom rooms                     # tests of one crate matching a name
cargo check --tests                                   # type errors without building test binaries
cargo nextest run -p cc_engine --test main macros     # integration tests matching a name (one binary per crate)
cargo clippy --workspace --all-targets -- -D warnings
cargo fmt --all -- --check                            # max_width = 120 (rustfmt.toml)
CC_UI_SNAPSHOTS=1 cargo nextest run -p cc_app snapshots # compare UI screenshots (tests/snapshots)
UPDATE_SNAPSHOTS=1 cargo nextest run -p cc_app snapshots # rewrite them after an intended UI change

# IFC validation (CI only; IfcOpenShell is never a build/runtime dependency)
pip install -r scripts/requirements-ifc.txt
cargo run -p cc_ifc --example export_ifc -- examples/casa_simples.ccad out.ifc
python scripts/validate_ifc.py out.ifc
```

CI (`.github/workflows/ci.yml`) runs fmt, clippy + tests (`cargo nextest run --profile ci`, then the doctests with `cargo test --doc`) on Linux (x86_64 and arm64)/Windows/macOS, the IFC validation job (exports `examples/casa_simples.ccad`, `crates/cc_ifc/tests/fixtures/features.ccad`, `structure.ccad`, `mep.ccad`, `arcs.ccad`, `roofs.ccad`, `phases.ccad`, `topography.ccad`, `curtains.ccad` and `profiles.ccad`), and a DCO check on PRs: commits must be signed off (`git commit -s`).

## Architecture

Rust workspace (edition 2024). Dependency direction: `cc_core` ← `cc_geom` ← `cc_views` / `cc_render` / `cc_ifc` ← `cc_engine` ← `cc_plugins` ← `cc_cli` (and `cc_engine` ← `cc_app`), and `cc_core` ← `cc_cad` ← `cc_engine`; `cc_skp` has no workspace dependencies and only `cc_engine` and `cc_plugins` (its ZIP reader) use it; `cc_core` ← `cc_script` ← `cc_geom` and `cc_plugins`, where `cc_script` (the Lua sandbox, JSON ↔ Lua conversion and the runtime of script pieces) builds Lua 5.4 from its C sources (`mlua` with `vendored`), so a C compiler is needed. `cc_core` knows nothing of geometry, views or UI; no crate depends on `cc_app`.

**Every user-facing operation must be reachable without the GUI**, as a command of `cc_engine`; the GUI, the `ccad` command line and the MCP server call the same commands. A new feature starts as an engine command (with a test in `crates/cc_engine/tests`), and the GUI calls it; do not put model logic in `cc_app`. The app holds a `Session` (`AppState::session`) and changes the model only through commands: `Session::run(SomeCommand { .. })` (typed, the same path as JSON commands), `actions::run_command` (errors to the status bar), or `engine_edit::{element, element_type, view, material, units, info, level, system}`, which turn a change on a copy of an object into its `*_set` command; dragged values pass a merge key (`Session::run_merged`) so they stay one undo step. The only direct document uses left are cancelling a dialog (`Session::undo_to`) and the untracked 3D camera. User documentation: `docs/automation.md` (and `docs/automacao.md`), `docs/interface.md` (and `docs/interface.pt-BR.md`) for the ribbon, tooltips, palette and UI tests; `docs/commands.md` is generated from the catalog (`reference.rs`), every parameter needs a doc comment, and `examples/small_house.ccmacro` is run by a test. Commands run through `Session::execute` are recorded while a macro is recording (edits only; dragged values once); macros are `cc_engine::script` files, the format `ccad script` runs.

- **cc_core** — the BIM model. `Project` (levels, materials, `types: BTreeMap<ElementTypeId, ElementType>`, `elements`, `views`) is the single source of truth. Every edit goes through `Document::edit` / `edit_merged`, which records a reversible `Transaction` (elements, views, types and project "settings" are tracked); continuous edits use `edit_merged` + `break_merge`. `Uid` is a persistent 128-bit id on project/types/elements (used as IFC GlobalId); `Document::new`, `from_ron` and `add_element/add_type` assign missing or duplicated ones. Files are versioned RON (`persist.rs`, `FORMAT_VERSION`): new fields must have serde defaults so older files load; bump the version for semantic changes. Old projects get missing ids and default annotation types on load.
- **Components** — `cc_core::component`: a `TypeData::Component { component, def }` holds a `ComponentDef` (params + pieces); types sharing `component` share the definition and differ in parameter values (the editor applies changes to all of them). Piece fields are `cc_core::expr` expressions (bounded parser, errors as values), except fixed `ComponentShape::Mesh` pieces (imported geometry); a sketched piece's `ProfilePoint`s run straight, along an arc (`radius`) or along part of an ellipse (`ellipse`) to the next point, and `cc_core::profile::from_curves`/`to_curves` turn sketch curves into these vertices and back; `ComponentDef::resolve` returns prisms (mesh pieces also carry their faces) in the component frame plus per-piece errors, and `cc_geom::component_parts` places them in the world (plans draw mesh pieces with `cc_geom::mesh_plan`). `.ccomp` files (`component_file.rs`) are validated on load. A `ComponentShape::Script` piece is Lua whose `geometry(p)` returns other pieces (`cc_core::component_script`: `ScriptEval`, hotspots, limits; `cc_script::object`: declarations, builders, `ScriptCache` and `shared()`, `sync`); its declarations are copied into `ComponentDef::params` (`from_script`; text, boolean, choice and material kinds, booleans stored as 1/0) and `hotspots`, elements keep `text_overrides` and moved `hotspots`, `ComponentDef::resolve_with` takes them in a `ResolveCtx`, and `cc_geom::resolve_instance`/`resolve_pieces` run scripts through the shared cache (a failing script keeps each element's last pieces); commands in `cc_engine::commands::component_script`. Doors and windows are components too (`cc_core::openings`): a `ComponentKind::Door`/`Window` definition with a `HostOpening` (width, height and default sill as expressions; `own_symbol` to draw its in-plan pieces instead of the category's swing or sash lines, `plan_only` pieces being 2D symbols with no solid) makes types of the door or window category, whose `ElementKind::Door/Window(Hosted)` elements cut that opening in their wall; the pieces are resolved with `WallThickness` defined, in a frame centered on the opening (x along the wall, y towards the side the door opens to, z up from the sill), mirrored by the element's flips (`cc_geom::opening_parts`, `ModelGeometry::opening_fills`). a window's `HostOpening::operation` (`cc_core::WindowOperation`: fixed, side-hung left or right, double, top-hung, horizontal or vertical pivot, sliding; `hinges` for plan swings (dashed arcs, `Drawing2D::dashed_arc`), `elevation_lines` for the elevation symbol that doors share, `ifc_panels`/`ifc_partitioning` for IFC export, `from_ifc_panels` for import; `openings::operable_window_def`, `OpeningNames::window_for`) sets its plan symbol; `ModelGeometry::opening_symbols` holds the elevation symbols of doors and windows as unfilled outlines just off both wall faces, which `projected::render` orders with the faces so what stands in front hides them, and plans dash a window wholly above the cut; a door's `HostOpening::door_operation` (`cc_core::DoorOperation`: one leaf hinged left or right, or a double door; `hinges` and `elevation_lines` as a window's, `ifc_operation`/`from_ifc` the IFC operation type, `ifc_panels` the `IfcDoorPanelProperties`) draws a swing per leaf, and `openings::operable_door_def`/`french_door_def` (glazed leaves over a `bottom_rail` parameter, `OpeningNames::door_for`) are the built-in ones, made by `door_type_create` (`cc_engine::commands::doors`); `ElementType::opening_size`/`default_sill`/`window_operation`/`door_operation` read either kind; the template's and IFC-imported door and window types are built-in definitions, and older files' fixed `TypeData::Door/Window` types become them on load (format 12).
- **cc_geom** — derived geometry, rebuilt from scratch by `ModelGeometry::build` whenever the document revision changes. Walls attached to a roof, ceiling or floor (`Wall::attach_top`) follow it: `attach_wall_tops` (after the slabs) gives a straight wall's `WallGeom` a `top_profile` along its centerline, from the planes of the target's faces turned down (reaching half the wall past them, breaking where the centerline crosses their edges or two planes cross), splits its columns there and rebuilds its solid; `EditCtx::finish` → `sync_attachments` drops references to deleted targets. Walls: joins are resolved per level on the body centerline (`Project::wall_axis`, which applies the wall's `LocationLine` and the type's core layers); an arc wall (`Wall::bulge`, see `cc_core::arc`) keeps a concentric centerline, its `WallGeom::arc` maps wall-local `(u, v)` (along the arc, to its left) to the plan, faces meet neighbors at the true crossings of their lines and circles, plans draw arcs as short chords and solids mark their curved facets `Face::smooth` (no seams, silhouettes only); base/top come from `Project::wall_base_z/wall_top_z` (top may be attached to a level). Walls meet where their drawn location lines end (`WallLine::drawn`). At a T, a layered wall's structure core (`WallGeom::core`) runs on through the outer layers of the wall it meets to that wall's core (`core_through` → `WallGeom::core_ends`, the host's `layer_gaps`), and plans draw the cleanup (`layer_span`, `layer_pieces`, `boundary_segments`; no line between cores of one material); bodies, volumes and 3D views are unchanged. `WallGeom` holds columns between openings; per-wall volume is analytic (the body solid omits caps at joins). `opening_parts` gives the pieces of a door or window (component pieces, or the boxes of `hosted_parts` for old fixed types) shared by the 3D view, plans and IFC. Pitched roofs come from the weighted straight skeleton in `skeleton.rs` (a wavefront simulation with edge and split events: sloped eaves move in at `1 / slope`, gables stay; `Roof::edge_slopes` overrides the slope or makes a gable per outline edge; faces per plane, hips, valleys and ridges; bounded, errors as values, the old lowest-plane construction as fallback), over outlines with openings (`Roof::holes`); `roofs.rs` builds the slab. `rooms.rs` finds a room boundary by tracing the face of the wall-footprint arrangement around the room point. Beams (and strip footings) resolve their ends in `beam.rs`: an end inside a structural column stops at its face, other ends reuse the wall joins (`resolve_join`) among beams at a common depth; beams are straight, but a strip footing may bend (`FoundationShape::Strip::bulge`, passed into its `WallLine`): its `BeamGeom::arc` maps local `(u, v)` like `WallGeom::arc`, and `FoundationGeom::arc` holds a `StripArc` (`strip.rs`: chorded outline, exact area and volume, smooth facets); `section.rs` turns column and beam sections (a type's structural profile, see *Structural profiles*, or its legacy fixed section) into non-overlapping parts and outlines; `analytical.rs` builds the analytical model (members between shared nodes) from columns and `ModelGeometry::beams`; `rebar.rs` lays out the bars of each `Rebar` set (an element hosted by a beam or column, removed with it) in its host, and places shaped bars (`ElementKind::ShapedRebar`: center lines in plan x/y and z above the level, no host, the type's diameter, imported property sets; what IFC import makes of an `IfcReinforcingBar` drawn as swept disks, typed by diameter and grade, and export writes back) where they are drawn, both in `ModelGeometry::rebar` for schedules, 3D and export.
- **cc_views** — views are queries over the model: `generate(project, geom, view)` returns a resolution-independent `Drawing2D` (lines with `LineStyle`, fills, anchored/rotated text in paper mm). Plans (`plan.rs`), projected views (`projected.rs`: elevations, sections, axonometric, painter's algorithm ordered by pairwise depth comparison of overlapping faces), legends, schedules (`schedule.rs`: a `ScheduleDef` in the view picks fields, sort, filter and totals; headers and some cells are i18n keys; `to_csv`), sheets (`sheet.rs`: `compose_sheet` lays out border, title block and scaled viewports in paper mm; the app paints it and `export.rs` writes it as SVG, a hand-written PDF with standard Helvetica, or PNG through resvg with text drawn as Inter outlines by `skrifa`; `view_on_paper` lays out any view the same way for `view_export`; `dxf.rs` writes a drawing as DXF R12 for `view_export`/`sheet_export`: a view at full size in millimeters (`DxfScale::model`), a sheet in paper millimeters, layers named by the caller (the element's category), dash patterns as line types, opaque fills as `SOLID` triangles, colors as the nearest ACI) and annotations (`annotate.rs`: room/door/window tags, grids, dimensions). Dimensions store points in the view's own drawing coordinates, so they work in any 2D view; in plans, elevations and sections each end may also reference a point of an element in its own frame (plus a height from its base or top in elevations/sections, through `View::projection`) or a level (`cc_core::dim_refs`), and every edit ends by moving referenced ends inside the same transaction (`EditCtx::finish` → `sync_dimensions`), so dimensions follow their elements and undo with them. A fill with alpha 0 is not hit-testable and only shows when its element is highlighted (room areas).
- **MEP** — `cc_core::mep`: plumbing systems and electrical circuits (`MepSystem`, kind, code, color, board, voltage) live in `Project::systems` (tracked as settings); pipes, conduits and cable trays are `ElementKind::Pipe/Conduit/CableTray(MepSegment)` runs with an elevation at each end and the systems they belong to (a tray's `TypeData::CableTray` holds width, height and `TrayStyle`; trays join only trays); a valve is `ElementKind::Valve(Valve { host, at })`, hosted by a pipe at a distance along it (its `TypeData::Valve` holds the `ValveKind`; diameter and system are its pipe's; repair drops one whose host is not a pipe, `remove_element`, copies and `pad_levels` keep it with its pipe); plumbing fixtures and electrical devices are components whose `ComponentDef::mep` holds fixture units or the device kind and power, connected by `Component::system`; a component's `ComponentDef::connectors` (name, system kind, position and direction expressions, diameter) are where runs join it (`cc_geom::component_connectors`): the network attaches each to a node of a system of its kind, and `mep_connect` starts branches there (components without connectors use their insertion point). `cc_geom::mep` makes the cylinders, tray channels (`ModelGeometry::segments`, `SegmentGeom::tray`) and valve bodies (`ModelGeometry::valves`) and `cc_geom::mep_net` the networks (`ModelGeometry::mep`: nodes where runs meet, edges, derived fittings, valves as nodes on their pipes, fixtures and devices attached to nodes), `cc_geom::sizing` sizes pipes and circuits from them, `cc_views::mep` draws plumbing and electrical plans (`ViewKind::FloorPlan { mep: Some(..) }`, the architecture faded; other floor plans leave MEP out; trays in electrical plans, valves in plumbing plans) and the device and valve symbols, `cc_views::diagram` the panel diagrams (`ViewKind::Diagram`, headings through the `label` of `generate_labeled`), `cc_engine::commands::mep` holds the commands and the circuit loads (`cable_tray` and `valve` the tray and valve commands; IFC export writes `IfcCableCarrierSegment` `CABLETRAYSEGMENT` and `IfcValve`). Systems come in families (`SystemKind::class`, `SystemClass`: plumbing, circuits, structured cabling `Data`, lightning protection `Lightning`); `commands::mep::check_fits` takes the families a member may join (pipes plumbing, conduits and trays circuits and cabling, lightning conductors lightning protection, devices their `DeviceKind::class`), and `MepSystem::panel` is a circuit's board or a data system's rack (`DeviceKind::is_board`). Lightning protection (`cc_core::lightning`): conductors are `ElementKind::LightningConductor(LightningConductor { run: MepSegment, role })` (role air, down or earth; `TypeData::LightningConductor` holds the diameter and material; they join only each other), air terminals and earth electrodes are device components (`DeviceKind::AirTerminal/EarthElectrode`, built-in definitions in `component::device_library`, made on demand by `commands::devices`); `cc_geom::lightning` finds the roof under a point (`surface_top`, where terminals and conductors land) and checks coverage (`check`: roof samples against each air termination point alone by the rolling sphere over the eaves plane, plus the mesh width on flat parts; `LpsClass` gives the radius and mesh), commands in `commands::lightning`. Structured cabling: data outlets (`MepData::Device::ports` jacks) and racks are device components; each rack feeds a `SystemKind::Data` system created by `rack_place`; `Project::outlet_cable` estimates each outlet's cables (`mep::cable_length`: up to the ceiling, across along the axes, down to the rack, plus slack), shown by `cabling_list`, `element_get` and the `CableLength` schedule field; commands in `commands::cabling`. Plans of the `MepDiscipline::Communications` and `Lightning` disciplines draw them (`cc_views::discipline_of`); IFC export writes conductors as `IfcCableSegment` `CONDUCTORSEGMENT`, terminals and electrodes as user-defined `IfcProtectiveDevice`, data outlets as `IfcOutlet` `DATAOUTLET`, racks as `IfcCommunicationsAppliance`, systems as `IfcDistributionSystem` `LIGHTNINGPROTECTION`/`DATA`.
- **cc_render** — offscreen wgpu renderer for 3D views (`Renderer3D`); `render_to_rgba` reads a frame back (home screen thumbnails).
- **cc_ifc** — IFC4 export with an in-house STEP writer (`step.rs`) and IFC2X3/IFC4 import with an in-house STEP parser (`parse.rs`, bounded nesting), geometry engine (`geometry.rs`: placements, curves, profiles, swept/CSG/B-rep/face-set items → world polygon meshes, depth- and size-bounded) and mapping (`import.rs`); no third-party IFC libraries by design. Import never drops a physical class: products become native elements only when a native element holds their geometry exactly (types matched by name and size; GlobalIds kept as `Uid`s), slabs become floors (with `Floor::openings` from profile voids and from openings that pass through them vertically) or, as base slabs shaped like slabs, foundation slabs (piles and pile caps written as base slabs stay components); anything else (including coverings, roofs, columns and beams voided by openings) becomes a component with `Mesh` pieces whose `ComponentDef::ifc` keeps the class and the type's property sets (`cc_core::properties`, values in SI units; instance sets live in `Component::properties`; objects of one name share a type only when their pieces and class are the same, and a type-less object whose placement lies outside its body is placed at the bottom center of its body, so identical objects written in world coordinates share one; `tests/rebar.rs`), with its openings subtracted by `csg.rs` (arena BSP-tree booleans, iterative and budgeted; also used for boolean results); `schema.rs` (IFC4 attribute layouts and type objects per element class) lets export write that class back. Column and beam types write their structural profile (`Exporter::profile_def`: the parametric `Ifc*ProfileDef` with its box centered on the position and the type's turn as its direction, else the placed outline as an arbitrary profile; a lipped Z has no IFC shape) in an `IfcMaterialProfileSet` per type and an `IfcMaterialProfileSetUsage` per element; level square-ended profile beams are swept along their axis, plain rectangles stay boxes, other beams faceted B-reps. Import reads columns and beams extruded from any profile (`Geometry::parametric_shape`, else the outline as a sketch of literal points, else its box; `Importer::profile_for` reuses a profile of the same name and shape). `tests/round_trip.rs` checks export → import. GlobalIds come from `Uid`s; derived objects (relationships, openings) hash the project uid with a tag.
- **Imported CAD drawings** — `cc_core::cad` holds the neutral drawing (`CadDrawing`: layers with RGB colors and file visibility, flat `CadPrim`s in drawing units — polylines with bulges, arcs kept as arcs, single-line texts with alignment, fills — extents and declared units) and the element `ElementKind::CadImport(CadImport)` (category `CadImport`, a `TypeData::CadImport {}` type created with the first import): owned by one view (`view`, like text notes; plans, ceiling plans, elevations, sections and legends, see `cc_views::hosts_cad`) and placed by `units`, `scale`, `position`, `rotation_deg` and `mirrored`, with `hidden_layers`, `color_mode` and `halftone`. The drawing is an `Arc` so undo steps and the repair check do not copy it; `repair` drops invalid primitives (copying only when needed), and the element has no phase. **cc_cad** reads files into it: an in-house DXF reader (`tokens.rs` ASCII/binary group pairs and code pages, `dxf.rs` sections/LAYER table/BLOCKS/ENTITIES, model space flattened while read, `flatten.rs` OCS → world with the arbitrary axis algorithm, nested/arrayed inserts with a cycle guard, depth, primitive and work budgets, layer 0 and BYBLOCK inheritance, `geom.rs` ellipses and de Boor splines, `text.rs` MTEXT codes); DWG goes through the `acadrust` crate (no default features, read from a byte buffer) on its own thread inside `catch_unwind`, its document written to binary DXF in memory and read by the same reader. `cc_views::cad` draws an import in its view under everything (thin lines with their own `Pen`, tessellated for the view scale), and `Drawing2D::background` makes `hit_test` pick it only where nothing else is; `graphics::apply` merges overrides into a line's own pen. `cc_engine::commands::cad` holds `cad_import`, `cad_layers` and `cad_layers_set`; `cc_engine::commands::cad_explode` holds `cad_explode`, which turns an import's visible primitives (`CadImport::layer_visible`) into native elements of its view through its placement in one undo step: polyline segments (bulges as arcs, negated under a mirror) and arcs (split past 270 degrees, circles as circles) become `DetailLine`s on a `LineStyleRef::Project` style per layer (found by name, else created with the layer's `cad::on_paper` color), fills boundary-less `FilledRegion`s of a solid type per color, texts `TextNote`s (top left 1.25 sizes above the baseline) of a `TypeData::Text` per size on paper (tenths of a millimeter), and visible pictures stay in the element (prims emptied; removed when none); `MAX_ELEMENTS` and `MAX_NEW_TYPES` refuse it before any edit, and the color mode and halftone are dropped (app: `UiCommand::Explode` on the Modify tab and the *Explode* button in `cad_ui::props`); `element_get`/`element_set` show and patch the placement without the drawing (`cc_engine::element_params`). Pictures share the element: `CadDrawing::images` holds `CadImage`s (a parallelogram `origin`, `u`, `v` in drawing units over a `cc_core::raster::RasterImage`: the file's own bytes, kept as base64 in project files, with format, pixel size and declared dpi), `cc_views::raster` reads sizes and decodes pixels (the `image` crate, size-bounded), `cc_views::cad` draws them as `Prim::Image` (under everything, faded with the element; `Prim::mapped` moves any primitive through an affine map), the app paints them as textured quads cached per picture (`paint.rs`), and exports write them (SVG `<image>` data URLs, PDF image objects with an alpha mask, PNG through resvg). `cc_cad::svg` reads SVG through usvg into the same drawing (curves flattened, single-outline fills, embedded pictures; texts skipped); `image_import` takes either and sizes pictures by their resolution or `width`. The app's tools snap to `CadImport::snap_features` (ends, midpoints, centers, lines, arcs) of the active view's imports; IFC export and 3D views ignore them.
- **cc_skp** — SketchUp (.skp) files, no external dependencies (its own ZIP, inflate/deflate and earcut). `SkpFile::open(..).parse(&ParseOptions)` gives an `SkpModel` (definitions, instances, faces, edges, materials, layers, pages; lengths in inches) from the current (ZIP) and legacy (version 3 to 2020) formats; `build_scene` flattens it to triangle meshes and `build_instanced_scene` keeps one mesh per definition plus placed nodes; `create::SkpBuilder` writes files and `edit::open_existing` rebuilds a builder from one. Derived from MIT-licensed code: the crate keeps `license = "MIT"` and its `LICENSE`. `cc_engine::skp` maps a parsed model to component types of fixed `Mesh` pieces (one per material, faces with holes triangulated): `skp_import` adds an element per placed component or group of the root (instances that differ only by a move or a plan rotation share a type; tilt, scale and mirror are built into the type; nested instances are flattened into their parent; the root's loose faces make one more element), `skp_component_load` makes the whole file one type; hidden objects and hidden layers are left out, materials are matched or added by name, and nesting depth and face count are bounded. `cc_engine::obj` reads Wavefront OBJ text into the same `skp::Converted` (in-house parser: `v`, `f`, `o`/`g`, `usemtl`, `mtllib` read by file name only next to the file, `Kd` colors; bad indices drop the face, bent faces become triangle fans, sizes bounded): `obj_import` (`units`, `z_up`, `merge`) places a type per object at the center of its footprint and its bottom; the app asks for those options in `obj_ui.rs` (*Insert → Import OBJ…*). Imported materials (`cc_engine::import_material::ImportedMaterial` in `Converted::materials`: name, color, opacity, texture) carry SketchUp textures (tile size in inches), OBJ `Kd` (read as sRGB), `d`/`Tr` and `map_Kd`, and glTF base color, `baseColorTexture` (buffer view, data URI or file beside; WebP source) and blended alpha; the color is the factor times the picture's average (`average_color`, linear), and the repeat the area-weighted meters per texture coordinate unit (`UvScale`), since textures are laid on face planes. Imported mesh pieces (SketchUp, OBJ, glTF, IFC) have their coplanar faces merged by `cc_geom::coplanar::merge`: neighbors across shared edges in one plane (1°, 0.01 mm) grow into one simple polygon, joining only along one run of edges so no hole or pinch forms; `Face::triangulate` splits a concave quad along its inner diagonal. `cc_engine::gltf` reads glTF 2.0 (`.glb` chunks, or `.gltf` JSON; buffers from the binary chunk, base64 data URIs or files by name only next to the file) into the same `Converted`: each root node of the scene with its descendants (node transforms composed, a depth limit and a visited set) is an object, triangles (modes 4 to 6, float or normalized integer positions, every offset and count checked) are turned from Y up to Z up, materials named with their base color as sRGB; required Draco/meshopt compression is refused; `gltf_import` (`merge`) places them like `obj_import` (`place_converted`), and `obj_ui.rs` serves *Insert → Import glTF…* too, asking only `merge`.
- **cc_engine** — the engine: a `Session` (the `Document` plus cached geometry, drawings and sheets) and a catalog of commands (`registry.rs`). A command is a parameter struct (`Deserialize` + `schemars::JsonSchema`; its doc comment is the description, its fields' doc comments the parameter docs) implementing `Command { NAME, KIND, run }`; register it in `registry!`. Names are `snake_case` (valid MCP/model tool names). Edits go through `commands::edit`, i.e. `Document::try_edit` + a repair check, so a command that would leave the model invalid is refused without an undo step. Levels, types, views and materials resolve by id or name (`refs.rs`); lengths in meters, angles in degrees, points `[x, y]`. `*_get` queries show the `params` that `*_set` commands merge (JSON merge patch over the model's serde form). Errors are values (`EngineError { code, message }`); `Session::execute` guards panics. Creation defaults shared with the drawing tools live in `defaults.rs`; localization (`i18n.rs`, the `t!` macro) lives here too and `cc_app::i18n` re-exports it.
- **Roof coverings and framing** — `cc_core::roofing`: `TypeData::Roof { covering, framing }` (serde defaults): a `TileKind` from the built-in catalog (`TileKind::spec`: least slope, weight, tiles per m², batten gauge, purlin span) and a `RoofFraming` (system None/Timber/TimberTrusses/Steel, material, purlin/rafter/batten `MemberSize`s and spacings, repaired on load). `cc_geom::roof_framing` frames each sloped underside plane of the roof's built solid, coplanar pieces together (battens at the gauge, rafters down the slope, purlins spread evenly; trusses: also king-post trusses across the eave direction of the largest face, cut from the faces sloping across them moved under the purlins, chords met at the apex, chords apart making separate trusses; steel: purlins only), as boxes across the roof plane; `build_slabs` stores it in `ModelGeometry::roof_framing` and adds the members as a `Category::Beam` solid of the roof element marked `Solid::secondary`: drawn, but left out of `ModelGeometry::body_of` (volume, joins, plan edges, IFC body), and section cuts hatch it in the framing's material. - **Sketches** — `cc_core::sketch`: a `Sketch` is the `SketchCurve`s (lines, bulge arcs, circles, whole or partial ellipses) an outline was drawn with; `Sketch::profile` chains them into loops (ends within `JOIN_TOL`, bounded, arcs and ellipses split every `ARC_STEP`) and returns the outline and its openings, or a `SketchError` with the point (open end, branch, crossing, apart, nested, openings where none are allowed). - **Terrain** — `cc_core::topography`: `ElementKind::Topography(Topography)` (category `Topography`, a `TypeData::Topography { material, contour_interval, major_every }` type created with the first terrain, in the earth material the template carries or `topography_create` adds) holds measured `points` (z above the level), a closed `boundary` (with an optional sketch) and `base_depth`; repair drops bad and repeated points, and its defaults and limits are the module's constants (`DEFAULT_*`, `MIN_CONTOUR_INTERVAL`, `EARTH_COLOR`, `earth_material`). `cc_geom::topography` triangulates the points inside the boundary with its edges as constraints (`spade`, constrained Delaunay, inside `catch_unwind`), gives the boundary the elevations all the points imply (barycentric, else the nearest point), closes the surface down to a flat base into a solid (`ModelGeometry::topographies`, analytic volume) and cuts `contours`; `cc_views::topography` draws plans (contours below the cut, the earth above it hatched). `cc_engine::commands::topography` holds `topography_create`, `topography_points_set` and `topography_type_create`; IFC export writes an `IfcGeographicElement` `TERRAIN` with `TOPOGRAPHY_PSET` (`ConstructCAD_Topography`), which import reads back. `sketch_set` takes a terrain's `points` with its curves (one step). `preferences.rs` holds the app preferences (`AppState::prefs`: theme, interface scale and text size, ribbon, tooltips, library/macros/projects folders, autosave, recent count), every eframe storage key with their validated load/save, `sync_look` (applies theme, zoom and font scale each frame) and the Preferences window (Ctrl+,; Cancel restores a snapshot); `plugins_ui.rs` loads the plugins folder into the session at startup (`Preferences::plugins_dir`; `plugins_off` are not loaded and run no code, `plugins_files` get the `files` permission; `AppState::replace_document` keeps the extension) and is the Plugins window (Installed and Available tabs; the index and archives are downloaded with `ureq` in background threads, never in tests) and the ribbon's *Plugin Commands* menu, which opens a command in the palette (`palette::open_command`; the palette lists `Session::commands`); `graph_ui.rs` is the visual programming editor (`AppState::graph`, a panel under the views: an in-house canvas on egui's painter, the node search over `graph_nodes`, an inspector, its own undo; runs go through `graph_run`; its keys take over while the pointer is over it, see `graph_ui::keys`); `library.rs` is the component library window (the `.ccomp` files of `Preferences::library_folders`, edited in Preferences → File locations, listed by `component_library_list`); `phases_dialog.rs` holds the Phases dialog, the phase rows of view and element properties and the Demolish tool, and `AppState::sync` sets the creation phase to the active view's (`phase_creation_set`); two-letter shortcuts are matched in `app.rs::shortcuts`.

## UI conventions

- **Familiar by design**: menus, shortcuts, panels and tools go where desktop CAD/BIM users expect them (quick access toolbar top-left, ribbon tabs, properties/browser docked left, standard Ctrl shortcuts and two-letter tool keys). Use general conventions only — never a specific product's icons, colors or wording; prefer neutral terms (Category, Type, Component — not "Family").
- Colors and fonts come from `theme.rs` (`LIGHT` and `DARK` hold the tokens; `PALETTE` reads those of the theme shown, which `theme::sync` follows every frame, and `theme::palette(ctx)` picks by the egui theme; the user picks light, dark or the system's with `ThemeChoice` in the Preferences window, and a text size (`theme::set_font_scale`) that scales the text styles and the property tables; 2D drawings keep white `paper` in both; Inter). Icons are our own SVG line drawings in `assets/icons/ui` (24 grid, white strokes, `stroke-width` 1.75, round caps/joins, soft fills at 20% opacity), rasterized by resvg per pixel size in two layers and tinted in `icons.rs`: strokes in the ink tone, soft fills in the tint tone (`icons::Tones`), plus an optional badge (new, import, export, remove).
- Ribbon, quick access and shortcut entries are `commands::UiCommand`s: label, shortcut, description, engine command and availability (with the reason) are defined there once; buttons and tooltips read them. Custom widgets report their role, label and state with `Response::widget_info`, so `ui_tests.rs` (egui_kittest) can find them by label; screenshot references live in `crates/cc_app/tests/snapshots` and run on request, since GPUs render slightly differently.
- Every modal uses `dialog::Dialog` (header with close button, footer buttons right-aligned: main action first, Cancel last; auxiliary buttons left; `danger` for destructive). Dialogs that edit data offer OK/Cancel and wrap edits in `dialog::session` so Cancel undoes them. A dialog is moved by its header and widens to fit its footer buttons; its header and footer follow a body wider than `width`, but a body must fit: in tests a dialog whose body overflows panics (`dialog::overflow`), and `every_dialog_keeps_its_body_inside` opens them all, so add a new dialog there. In table cells use `table::checkbox`/`labeled_checkbox`/`boxed` (a plain checkbox has no box in a flat cell) and `table::button_row` for several buttons; a `table::row` value is clipped to its cell.
- Property grids use the shared `table.rs` primitives (collapsible `section`, two-column `row`).
- No hard-coded interface text: keys live in `assets/i18n/*.ftl` (`pt-BR` is the reference, then `en`, `es`, `fr`, `de`, `it`, `lo`, `pl`, `uk-UA`, `zh-TW`, `zh-CN`, `ja`), read with `t!` / `tr`. A test scans the sources and fails if any key used in code is missing from a language, and another fails unless every language has the same keys and placeholders, so add every new key to all of them.

## Robustness rules

- **Non-test code never panics.** No `unwrap()`, `expect()`, `panic!`, `unreachable!`, `todo!`, `unimplemented!` — the workspace denies them in clippy (`[workspace.lints]`), and `clippy.toml` allows them only in tests. Return errors and propagate with `?`, or use `let … else`, `if let`, `ok_or(…)?`, `unwrap_or*` where the fallback is truly correct (never one that silently corrupts a document).
- **No `unsafe`** (`unsafe_code = "forbid"`).
- **Files are hostile input.** `.ccad` files pass through `Project::repair` on load (`persist::from_ron_with_repairs`): invalid numbers and dangling references are removed or reset and the app reports how many. Use `get()` for indices that come from files, selections or arithmetic on them; guard divisions by zero and NaN/inf.
- **Bound recursion and loops** over model references with visited sets or limits (hosting can be cyclic in a crafted file; see `EditCtx::remove_element`).
- **Last-resort guard:** opening, saving and exporting run inside `actions::guard` (`catch_unwind`); a panic becomes an error message and the open document is kept. Keep `panic = "unwind"` (the default profile).
- **Tests run with cargo-nextest** (`cargo nextest run`; install it with `cargo install cargo-nextest --locked`), in every session and in CI; doctests still need `cargo test --doc`. Settings live in `.config/nextest.toml` (the CI uses its `ci` profile).
- **Prove it:** every crash fix comes with a small synthetic regression test that failed before the fix.
- **Integration tests are one binary per crate**: `cc_engine`, `cc_ifc`, `cc_plugins` and `cc_skp` set `autotests = false` and build only `tests/main.rs`, which declares each file of `tests/` as a module; a new test file needs its `mod` line there (`every_test_file_is_a_module` fails otherwise).
